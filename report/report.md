\# Copilot-Assisted Packet Sniffer: Seeing the Network (Ethically)



\## Introduction



The purpose of this project was to build and test a Python-based packet sniffer using the Scapy library. The project was designed to demonstrate how network packets can be captured and decoded while also applying ethical and privacy protections.



Packet sniffers are powerful tools because they can observe network traffic moving through a network interface. Depending on the traffic and protocols being used, packet information can include IP addresses, transport protocols, DNS queries, and application-level information. Because packet capture can expose sensitive information, this project was designed to capture only authorized traffic and redact sensitive information before displaying it.



The project was developed using Python, Scapy, Git, and GitHub. The packet sniffer was tested on the student's own computer using the authorized Wi-Fi interface. The program was configured to capture a maximum of 25 packets and apply a TCP/UDP filter.



\## Lab Environment and Ethical Scope



The packet sniffer was tested on the student's own Windows computer and its authorized network interface. The active interface used during testing was the Wi-Fi adapter. Traffic was generated by the student's own computer during testing.



The project followed the ethical requirements provided for the assignment. The tool was not designed to capture other people's traffic, bypass operating system permissions, hide activity, or maintain persistence.



An interface allowlist was included in the program so that only an authorized interface could be used. The program also limits the number of packets captured and applies a Berkeley Packet Filter (BPF).



\## Packet Capture



The initial packet capture test confirmed that Scapy could successfully capture traffic from the Wi-Fi interface. The test displayed TCP and UDP packets and demonstrated that both IPv4 and IPv6 traffic could be observed.



The final version of the program was configured with the following settings:



\- Interface: Wi-Fi

\- Packet limit: 25

\- BPF filter: tcp or udp

\- TCP and UDP identification

\- IPv4 and IPv6 address handling

\- DNS query handling

\- Sensitive information redaction



The packet limit was used to prevent the program from continuously capturing traffic. The final test successfully captured 25 packets and then returned to the command prompt automatically.



\## Packet Decoding



The program identifies whether captured packets contain IPv4 or IPv6 information and extracts the source and destination addresses. IP addresses are masked before they are displayed.



The program also identifies TCP and UDP traffic. DNS queries can be decoded when DNS information is present in a packet. The program was designed to inspect HTTP-like TCP payloads without displaying an entire payload.



During testing, the packet output demonstrated TCP and UDP traffic as well as IPv4 and IPv6 traffic. The output provided evidence that the packet sniffer was successfully processing captured packets.



\## Redaction and Privacy Controls



Redaction was one of the main ethical safeguards in the project. The goal was to prevent sensitive information from being unnecessarily displayed in the packet output.



The program partially masks IPv4 addresses. For example, an address such as 192.168.1.177 is displayed as 192.168.1.xxx. IPv6 addresses are also partially masked.



The program also includes redaction rules for information that could contain sensitive credentials or personal information. These rules include:



\- Email addresses are replaced with \[REDACTED\_EMAIL].

\- Authorization values are replaced with \[REDACTED].

\- Cookie values are replaced with \[REDACTED].

\- Password values are replaced with \[REDACTED].

\- Token values are replaced with \[REDACTED].

\- Session-token values are replaced with \[REDACTED].



The program applies these protections before displaying relevant packet information. This reduces the possibility of accidentally exposing sensitive information in the terminal output or project evidence.



\## Unit Testing



Unit tests were created to verify that the redaction functions work correctly. The tests cover email addresses, passwords, tokens, cookies, IPv4 addresses, IPv6 addresses, and combined sensitive information.



The tests were executed using:



python -m unittest discover -s tests -v



All seven tests passed successfully. This provided evidence that the redaction functions were operating as expected.

\## Risks of Packet Sniffers



Packet sniffers are powerful because they can observe network communications and provide information about devices, protocols, addresses, and application activity. Depending on the protocol, captured traffic may contain information that should remain private.



Unauthorized packet capture can create privacy and security risks. Credentials, session information, emails, and other sensitive data may potentially be exposed if traffic is not properly protected.



For this reason, packet capture tools should only be used on systems and networks where the user has authorization. Limiting the capture interface, limiting the number of packets, applying filters, and redacting sensitive information are important safeguards.



\## How Defenders Can Detect Misuse



Defenders can look for unusual packet-capture activity through endpoint monitoring, security logs, application inventories, and network monitoring. They can also use access controls to limit who has permission to perform packet capture.



Security teams can investigate unexpected network-interface activity, unauthorized packet-capture software, unusual administrative activity, and other indicators that a packet-capture tool may be operating without authorization.



Network segmentation and encryption also reduce the amount of useful information that can be obtained from unauthorized packet capture.



\## Copilot Use and Reflection



GitHub Copilot was used as an AI development assistant during this project. It was used to help with boilerplate code, packet-processing structure, and unit-test scaffolding.



The generated suggestions were reviewed rather than automatically accepted. The project was modified to include an authorized interface allowlist, a packet-count limit, a BPF filter, and redaction controls.



Suggestions that would involve capturing other people's traffic, bypassing operating-system permissions, adding stealth features, maintaining persistence, or hiding activity were not used.



The project demonstrated that AI assistance can help with software development while still requiring the developer to review the generated code and enforce ethical and security requirements.



\## Conclusion



This project demonstrated how packet sniffing can be used as a network-learning and defensive security tool when it is performed within an authorized environment. The final program captured a limited number of TCP and UDP packets, decoded network information, and applied privacy protections before displaying data.



The project also demonstrated the importance of reviewing AI-generated code. GitHub Copilot can assist with development, but the developer must ensure that the resulting program follows security, privacy, and ethical requirements.



Overall, the project combined packet capture, network protocol analysis, Python development, automated testing, Git version control, GitHub, and responsible use of AI-assisted development.
